So: **two real findings, one spurious, the rest timeout-only** — the same shape
the x86 run had, which is itself a useful cross-check.

### 1. `pharo-rdbms-pharo-sqlite3` — 111 errors, all one signature

    111  Error: Module not found.

An FFI library-resolution gap, not a JIT miscompile: stock Cog opens the sqlite3
shared library and we do not. Same family as the already-fixed Athens/cairo and
LibTTY resolution gaps (`aade2dde`, `cb53b45f`). Not seen in the x86 sweep, where
this package sat in the load-failed bucket. **New, and actionable.**

### 2. `rko281-porpoise` — the weak-reference test is still JIT-only

    FAIL PropertyManagerTest>>testPropertyManagerValueWeakness

This is the test the x86 document called "the one finding that correlates across
suites". `88ce3fee` fixed `WeakOrderedCollectionTest` — which no longer fails in
50 consecutive runs — but did **not** fix this one, so there is a second
weak-reference retention path and this is a reproducible representative of it.

That matters because the `WeakOrderedCollectionTest` "~2-in-16 residual" I had
been carrying turned out to be unreproducible measurement noise. This is the
real remaining case, and unlike the residual it is a stable target: the four GC
provenance probes (`PHARO_WATCH_ROOT_CLASS`, `PHARO_WATCH_HEAP_CLASS`,
`PHARO_WEAK_SURVIVOR_PATHS`, `PHARO_WEAK_SURVIVOR_CLASSES`) apply directly.

### 3. `driolar-soccertheory-pharo` — CLOSED by the CWD fix

The x86 run's largest "real" finding was 12 `XMLFileException: soccerML.dtd does
not exist` errors present only under our VM, attributed — reasoned, not measured
— to our `chdir()` to the image directory. That attribution is now **confirmed**:

    x86, before d1cd608e   cog err=0    ->  jit err=12      (12 JIT-only)
    arm, after  d1cd608e   cog err=13   ->  jit err=12 t=1  (12 SHARED, 0 JIT-only)

The twelve failures moved from JIT-only to shared: with the CWD no longer moved
out from under the image, both VMs resolve `soccerML.dtd` the same way and both
fail to find it. The only residue is one test that is an `ERR` on Cog and a
`TIMEOUT` on ours — the same test, a different manifestation.

### 4. Spurious

`mumez-redistick`'s counters are byte-identical on both arms (`fail=6 err=4`);
the flag column over-reports, exactly as it did on x86.

## Three attempts, and what each cost

Worth recording, because two of the three produced nothing and all three
failures were ours:

1. **Attempt 1** — the box built the tree as of 2026-06-10. `clone-and-build.sh`
   took a pre-existing `origin/jit-arm-linux` (a spot-interruption autosave)
   unconditionally, and reported success. Fixed `07091eeb`: a remote work branch
   is reused only if it already contains base, and the resolved commit is echoed.
2. **Attempt 2** — 152 of 223 custom-VM runs evaluated nothing. Fallout from
   `d1cd608e`: with the CWD no longer moved, eval mode writes `startup.st` into
   the working directory, and 24 workers shared one. Fixed `41863894`: both arms
   run from `$OUT/wd-$LABEL`, and the VM now prints a loud error if its
   `startup.st` is still on disk at exit. That attempt then died at 158/200 to a
   **spot reclamation** (`Server.SpotInstanceTermination`), losing everything on
   the instance store.
3. **Attempt 3** — this one. On-demand, per-package working directories, and
   `PRESERVE_S3` uploading each package's results as they appear (`1b9b7a56`),
   so a reclaim would now cost minutes rather than the run.

Cost: attempts 1-2 ran on a 64-vCPU c7g.16xlarge (the arm config's default) at
roughly $2.3/h for about an hour and produced nothing. Attempt 3 ran on the
16-vCPU c7g.4xlarge at ~$0.60/h — the figure that should have been quoted from
the start.
