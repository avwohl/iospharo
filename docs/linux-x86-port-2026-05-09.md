(this session):

    with its body — keeps the source list and content guard
    decoupled.

### Tier-1 IntegerTest hang — narrowed but not fixed

Investigation findings (2026-05-09):

  - The hang is `IntegerTest>>testNumberOfDigits` exceeding the 80 s
    soft-watchdog and failing the `prim-stuck` hard-watchdog tier.
  - **`testNumberOfDigits` runs in 131 ms standalone** when invoked
    via `IntegerTest new testNumberOfDigits` under JIT-on / Sista-off.
    Same 131 ms under JIT-on / Sista-on.
  - Inside `SUnitRunner runAllTests` the same test exceeds 80 s.
    A ~**600× slowdown** only in the SUnit-harness context, not in
    standalone invocation.
  - Reproduces under both `PHARO_NO_SISTA=1` (tier-1 only) and
    `PHARO_SISTA_DISPATCH=1` (tier-1 + tier-2) with identical
    timeout shape, so this is **tier-1, not Sista**.
  - The watchdog DNU on a malformed Process Oop
    (`0x...000000` — 24 trailing zero bits) only fires under specific
    cumulative conditions (full SUnit, after many classes).  Looks
    like JIT state corruption in the watchdog-suspend path, but
    only after warmup with hundreds of method compiles ahead of it.
  - Test body: 3046 iterations of `b raisedTo: n` + 6 asserts on
    `numberOfDigitsInBase:` per iteration (b=2..32, n=1..1000//b).
    Heavy big-integer arithmetic; the 30x JIT-on-vs-no-JIT slowdown
    quoted earlier in this doc is a class-average — `testNumberOfDigits`
    is far worse.

Hypotheses for the 600× context-dependent slowdown (not yet
verified):

  1. Method-map / IC pollution from prior tests' polymorphic call
     sites pushes `numberOfDigitsInBase:` into a deep-recompile or
     megacache-miss state.
  2. Code-zone fills enough that JIT methods get evicted and
     re-compiled mid-loop.
  3. Forked test process priority interaction with
     `relinquishProcessorForMicroseconds:`-based watchdog — the
     test process at P40 and watchdog at P60 may not be yielding
     correctly under heavy compile-bound load.

### gdb attach (2026-05-09) — refined picture

`sudo gdb --batch -p $(pgrep test_load_image)` succeeds (with
`/proc/sys/kernel/yama/ptrace_scope=1`, sudo bypasses the
restriction).  Two consecutive samples 3 s apart on the hung VM
(full SUnit, JIT-on / Sista-off, IntegerTest::testLargePrimesUpTo
visible as the last `RUN: …` line, results file 60 s+ stale):

```
Thread 1 "test_load_image":
  #0 __syscall_cancel_arch
  #1 __internal_syscall_cancel  (nr=230, clock_nanosleep)
  #4 usleep                     (useconds=10000)
  #5 pharo::Interpreter::primitiveRelinquishProcessor(int)
  #6 pharo::Interpreter::executePrimitive(int, int)
  #7 pharo::Interpreter::sendSelector(pharo::Oop, int)
  #8 pharo::Interpreter::interpret()
  #9 main
```

Both samples identical.  The VM is voluntarily idle in the
relinquish primitive's `usleep` fallback (capped at 10 ms by
`MAX_SLEEP_US`), spinning a `relinquishProcessorForMicroseconds:
50000` loop because no lower-priority process is in the ready
queue when the runner's main loop wakes.

The malformed-Process-oop DNU (`#suspend not understood by
rcvr=0x...000000`, 24 trailing zero bits, classIdx=3075,
classOf=nil) is the watchdog *firing successfully* (deadline
expired) but the captured `testProcess` slot now holds garbage —
either (a) a stale pointer to a moved/GC'd Process, or (b) a
miscompiled `forkAt:` return value.  Reproduces under Sista-off
JIT-on, so the closure-binding-or-GC bug is in tier-1.

### Root cause: rebuildFreeListAfterCompact 4 GB memset

Investigation 2026-05-09 (later): the testNumberOfDigits "hang" did
NOT reproduce in any current build (Release, Debug+no-LTO; freshly
prepped image, freshly downloaded image; with watchdog
instrumentation, with stock runner).  It passed in 131 ms each time.
Instead, gdb attach during a different stall pointed at
`ObjectMemory::updatePointersAfterCompact` — full GC was running and
RSS had grown to 4.4 GB despite a 227 MB live heap.

Cause: `ObjectMemory::rebuildFreeListAfterCompact` did
`std::memset(oldSpaceFree_, 0, oldSpaceEnd_ - oldSpaceFree_)`.
`oldSpaceEnd_` is `oldSpaceStart_ + oldSpaceMmapSize_`, and
`oldSpaceMmapSize_` is the 4 GB virtual reservation that
`test_load_image.cpp:861` hands to `MemoryConfig::oldSpaceSize`.  The
mmap is `MAP_ANONYMOUS | MAP_PRIVATE` so pages are zero-on-first-touch
and lazy-committed — until the first fullGC's memset writes every
page in the entire 4 GB tail, committing all of them.  Subsequent
GC walks (mark / planCompact / updatePointersAfterCompact) only
touch the live 227 MB, so they're fast on their own — but the memset
that runs at the end of each compact takes seconds and balloons RSS
to the full 4 GB on the very first GC.

The memset is also unnecessary: every scanner in the VM (objectScanner,
markPhase, updatePointersAfterCompact, scanRegionForYoung,
forSomeInstancesOf, …) walks `oldSpaceStart_..oldSpaceFree_` only.
Nothing reads past `oldSpaceFree_`, and `allocateRaw` zero-inits
slots itself (`ObjectMemory.cpp:162-164`) when it bumps the pointer.

Fix (`ObjectMemory.cpp:3299`): drop the 4 GB memset; instead
`madvise(MADV_DONTNEED)` the page-aligned tail so the kernel can
reclaim physical pages.  Confirmed locally:

  Before fix (Release VM, fresh image, full SUnit run):
    RSS ~4.3 GB within 25 s of VM start
  After fix:
    RSS ~186 MB at the same point

Earlier `IntegerTest>>testNumberOfDigits` "hang" was almost certainly
this — testNumberOfDigits is a heavy big-integer arithmetic test
that triggers GC; each GC paid the multi-second 4 GB memset, and
after enough GCs accumulated within the 80 s soft-watchdog window
the test exceeded its budget.  The Process-oop DNU at watchdog fire
was downstream noise from the watchdog flowing through a deeply
contended scheduler, not closure-slot corruption.

### Per-class pace bottoms out at ~1239 steps/sec

The dominant blocker now is throughput.  Step rate from `[PROGRESS]`:

      t=10s  → t=20s   8 331 142 steps/sec  (warmup: image load, JIT
                                              compile burst)
      t=30s  onward    1 137 – 1 353 / sec  (steady state, entire run)

That's a 6 700× drop from warmup, and it's stable for 45 minutes.  At
1239 bc/sec the 768 classes would take ~80 hours — matches what we
saw (7 classes in 45 min ≈ 6 min/class).  Same shape as the gdb
attach finding from earlier today (stuck in
`primitiveRelinquishProcessor`'s `usleep` fallback): the runner's main
loop sleeps 50 ms between iterations because no lower-priority
process is in the ready queue, so each wake interpets ~62 bytecodes
before relinquishing again.  20 wakes/sec × 62 bc = 1240 bc/sec.

Tests still complete because the suspended test process *does* run
during those wakes — but the long-tail throughput is gated by the
50 ms sleep, not by the JIT.

Earlier observations suggested "JIT-on running ~30x slower than no-JIT"
based on SUnit-time data.  That was misleading — it captured the
JIT-compilation deferral phase plus first-use compile-burst, not
steady-state JIT.

A/B with explicit fib28 warmup to cross the 120 M-step deferral floor.
Same exact workloads run before and after warmup:

```
                Pre-warmup     Post-warmup     Δ
                (interp via    (JIT engaged)
                 deferral)
  sum1M           46 ms          44 ms        -4%
  sum2M           89 ms          89 ms        equal
  fib20            2 ms           2 ms        equal
  fib25            —             19 ms
  fib28           84 ms          79 ms        -6%
  fib30            —            175-188 ms
```

Tier-1 JIT is at **parity or slightly faster** than the interpreter
across send-recursive (fib) and block-iteration (sumTo) workloads.
Three iterations of each give run-to-run results within 1-3 ms.

(Earlier `sumTo10M`-after-fib28+30 hang in a separate run is real but
non-reproducible from a fresh image; likely state-dependent IC churn
that this clean A/B doesn't trigger.  Not chasing further unless it
shows up as a recurring problem.)

### IC hit rate investigation — not a Linux-x86 bug

Initial concern: cumulative IC hit rate showing ~31% on Linux x86_64
seemed low vs an assumed Mac arm64 baseline of "~99%."  After
delta-stats analysis (parsing successive `[JIT] Stats:` print-outs to
isolate steady-state behaviour from startup/compile churn) the picture
clarifies:

```
Sample-to-sample deltas (fib28 in steady-state JIT, x86_64 Linux):
  Δsends       65 536
  ΔIC events   ~21 800   (33 % of sends touch IC)
  ΔIC hits     ~6 400
  ΔIC hit rate 28-29 %    (consistent across 10+ samples)
```

So ~33 % of sends use the IC, of which ~28 % hit.  The other 67 % of
sends bypass IC via the J2J chain (cached path activations) which has
its own dispatch.  Steady-state fib28 runs in 14-15 ms = ~4-5x faster
than the no-JIT interpreter (66 ms) — same ballpark Mac arm64
reports for fib28 with eager JIT (19 ms on M-series silicon).

The "99 % IC hit" value the original analysis quoted was for a
different workload shape (`block(500K)` tight loop with one repeated
selector); send-heavy recursion intrinsically has lower IC hit rate
on this VM's IC design (6-entry IC, no megacache backstop in the
fast path).  The codebase's Mac docs (`docs/bench-results-2026-04-25.md`)
already note `block(500K)` is *slower* under JIT than the interpreter
on Mac — i.e. the IC isn't the perf story for this VM, fast-path send
dispatch is.

**Conclusion**: no Linux-x86_64-specific IC bug.  The steady-state
JIT-vs-interpreter ratio on x86_64 is comparable to Mac arm64.
Improving IC hit rate further is a *platform-agnostic* optimization
project, not gating x86_64 readiness.

## Sista x86_64 port — current state

History:

  - `fc1ab6a8` split SistaLowering.cpp into per-arch siblings
    (`SistaLowering_arm64.cpp` + `SistaLowering_x86_64.cpp`), with the
    x86_64 file initially bailing on every op.
  - `ea4cce39` (MVP) lowered the basic 7-op set: kLoadReceiver,
    kLoadTrue/FalseOop, kLoadTemp / kStoreTemp, kLoadLiteral,
    kConstantOop, kReturn.  38% method compile rate, 0 SIGSEGVs.
  - `e39540ce` extends that with the arith/compare/branch tier:
    kPrim{Add,Sub,Mul}Int, kPrim{Lt,Le,Gt,Ge,Eq,Neq}Int +
    kPrimIdentity{Eq,Neq} (cmp + jcc materialise into trueOop/falseOop,
    with cmp→branch fusion), kPrimTagCheckInt (deopt on miss),
    kBranch / kBranchIfTrue / kBranchIfFalse, kPhi (pre-alloc +
    fillPhis from outgoingStack), kLoadStackSlot, kLoadInstVar,
    kStoreInstVar (helper-emit branch).
  - `b47ec04a` fixes three latent correctness bugs in the above:
    (a) Implicit fall-through phi-fill — block walk only filled phi
        regs in explicit-terminator handlers; non-terminator blocks
        skipped phi-fill, leaving successor phis with garbage that
        cascaded as `#isInteger` / `#+` DNUs deep in
        `SnapshotOperation>>performSnapshot`.
    (b) `emitDeopt` stackBase parameter — hardcoded skip-2 was right
        for arith but wrong for kPrimTagCheckInt (skip-1).  Mis-spilled
        the deopt frame.
    (c) Add/sub used 64-bit `jo` for overflow detection, but tagged
        SmallInts have a 60-bit value range — `jo` was too permissive,
        silently producing out-of-range tagged values.  Replaced with
        the bit-62/63 mismatch trick on the tagged result.
    Plus a kPrimTagCheckInt type-narrowing fast-path matching arm64.

`SistaLowering_arm64.cpp` is 5237 lines; the x86_64 sibling is now
658 lines and growing as op coverage expands.  Tier2Compiler.cpp
(2267 lines) still emits arm64 directly; not yet ported, but the
Sista-lowering bail path means tier-2 stays off for any op the
x86_64 lowerer can't yet emit.

Remaining op tiers (in expected priority order):

  1. **Sends** — kSendCallHelper, IC-inline send paths, super sends.
     Biggest payoff: most methods that bail today bail here.  Needs
     a portable IC-inline emit (the runtime helper signature is
     already arch-neutral).
  2. **Allocation** — kAllocateNew / kAllocateNewIndexable bumps,
     plus the GC-fast-path emit.
  3. **Float arith** (kPrimFloat{Add,Sub,Mul,Div}, kPrimFloatLt…) —
     uses xmm0/xmm1 + ucomisd on x86_64.
  4. **Block alloc + closures** — kAllocateClosure / kBlockEval.

Each new op lands with `[SISTA-x86] OK` trace + a SUnit run as the
correctness gate.

Other deferred work (perf, optional):

  - **SimStack on x86_64** (~10-20% on tight loops).  Lift the
    `#ifdef __aarch64__` in `JITCompiler.cpp:946-1231` and write
    the x86_64 equivalent (r12-r15 are callee-saved in SysV; arm64
    uses x19-x22).
  - **Hand-written x86_64 J2J trampoline** — parallel of
    `TrampolineAsm.S`.  C++ fallback already works; this would
    speed the J2J chain.

  - Pi 5 bare-metal Ubuntu 25.10, ARM64, gcc 15: SUnit 351/351
    on OrderedCollectionTest, full bench `block(500K)` = 134ms
    (after JIT validation fix in commit `2d2b4fa`).

  - The same source tree builds and runs there with no Linux-arm-
    specific changes — `bash scripts/build-linux.sh` works because
    the existing arm64 lowering + arm64 stencils don't care about
    OS, only about ISA.

Implication: when Sista x86_64 lowering lands, the regression test
for "did I break arm64 Linux" is a build + SUnit run on the Pi.  TBD
how this Linux x86 box reaches the Pi (the user mentioned a Pi is
available for testing — we need to confirm the access path: SSH from
this box, SSH from Mac, manual sync, etc.).

## File map for x86_64 JIT work

  src/vm/jit/
      sista/SistaLowering.{hpp,cpp}    ← gradual op-by-op port
      Tier2Compiler.{hpp,cpp}          ← parallel direct-emit path
      JITRuntime.cpp                    ← runtime helpers, arch-neutral
      JITCompiler.cpp                   ← stencil stitcher, mostly arch-neutral;
                                         applySimStack() is __aarch64__-only
      generated_stencils_arm64.hpp     ← committed, used on arm64 hosts
      generated_stencils_x86_64.hpp    ← committed, used on x86_64 hosts
      TrampolineAsm.S                   ← arm64 hand-written; x86_64 uses C++ fallback

  scripts/extract_stencils.py           ← Mach-O only; if regenerating x86_64
                                         stencils on Linux is ever needed,
                                         add an ELF reader path
