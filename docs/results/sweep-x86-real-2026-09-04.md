# Full SUnit sweep on REAL x86_64 Linux, 2026-09-04

The first complete 2047-class sweep of this VM on native x86_64 hardware — not
Rosetta.  AWS `m6a.4xlarge` spot (`i-069e3881670b0cac0`, us-east-2), Ubuntu
24.04, tree built on the box, fake-GUI-prepped image, `scripts/aws/x86-gui-sweep.sh`
with per-batch S3 checkpointing.

It ran as two attempts against one `RUN_ID`.  The first box was reaped at
index 500; the second RESUMED from the S3 checkpoint at index 501 rather than
restarting, which is the first real use of `START_AT` earning its keep.

## Two things this settles that the Rosetta sweep could not

**The threaded-FFI batch is genuinely fixed.**  Batch 1801-1850 — the one that
used to burn the whole 1800 s `PER_BATCH_TIMEOUT` on both arches (defect #26)
— ran `rc=0` in **137 s** on real hardware.

**The fake-GUI `KeyboardKeyTest` wedge is macOS-specific.**  Batch 651-700, the
batch that costs 20 of 51 classes to a wedge on this Mac, ran `rc=0` in 126 s
here.

## The rc=137 batches are the sweep's own early kill, and they cost nothing

Roughly a third of batches came back `rc=137`.  That is `sunit-sweep.sh`
killing a VM that has already written `/tmp/sunit_run_completed.txt` and is
still alive `SHUTDOWN_GRACE=30` s later.  **Every one of them wrote all 51
class totals and `*** BATCH COMPLETED`**, which is why the sweep still reports
2047 classes.  What happens in that window was measured on the box afterwards
(defect #29): the VM's own shutdown takes **660 ms** end to end, and the time
is ~22 s spent inside the IMAGE between writing the marker and calling the
quit -- mostly idle (845M bytecodes in the 10 s before the marker, 31M in the
10 s after).  Timed three times on batch 51-100: 21 s, 19 s, 23 s.  So this is
a slow tail that sometimes crosses the 30 s `SHUTDOWN_GRACE`, not a wedge, and
the earlier claim in this repo that `primitiveQuit` is never reached was
wrong.

## Caveat on `TraitFileOutTest`

Its 2 ERRORs here are the working-directory artifact of defect #28, not a VM
defect: this sweep ran before `RUN_FROM_IMAGE_DIR` was defaulted on.  A sweep
on the current `sunit-sweep.sh` should show it clean.

### `LinkInstallerTest` is the new one, and it is not the JIT

`testPropagateNewClassScopedLinks` fails **4 of 4** runs, on arm64 AND x86_64,
with `PHARO_NO_JIT=1` as well as with the JIT on, while Cog passes 40/40.  Both
its reported failures are the same test: `[Assertion failed]` plus the
tearDown's `[Leaked metalinks]`.

Two things it is NOT, each checked: it is not arch-specific (arm64 and x86_64
on this Mac fail identically), and it is not the random node the test picks —
`allChildren atRandom` does vary run to run on our VM (three launches give
three different sequences from `(1 to: 100000) atRandom`), so a 4-of-4 failure
is node-independent.

### Two "x86-only" entries were an artifact of batch composition

`LinkInstallerTest` and `SpHorizontalBoxLayoutTest` were listed above as
x86-only because arm64 ran them clean in the full sweep.  Run in a small batch
on this Mac, **both fail on arm64 too** — and `SpHorizontalBoxLayoutTest`
passes 21/21 when run in a 2-class batch, so its failure is batch-order
sensitive rather than architectural.  Neither is an arch difference.
