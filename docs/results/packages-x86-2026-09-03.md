## What differs between the arches, and what does not

FAIL is identical on both: 14 DataFrame + 2 PolyMath, the same selectors.  No
x86-only failure exists in the package tier.

ERROR is 24 on x86 against 16 on arm.  The delta is XMLParser 5-vs-0 and
PolyMath 19-vs-16, and PolyMath also reports 55 MORE passes on x86 than on arm
(1447 vs 1392) with one fewer timeout -- i.e. the two runs did not execute the
same set of cases, which is what a per-class timeout boundary looks like rather
than a codegen difference.  Both remain to be attributed case by case.

## DataFrame and Fuel first reported NO RESULT, and that was load, not the VM

The first x86 pass wrote no `result.txt` for either package: the test eval
started (1.7M activations, 3353 methods compiled in the DataFrame log) and the
VM exited normally without reaching even the first per-class `PARTIAL` write.
Both packages were re-run alone, same binary, same reused image, same
`PER_CLASS_TIMEOUT`, and both produced results identical to arm64 --
DataFrame 27 classes 839 P / 14 F, Fuel 2 classes 19 P.

The first pass overlapped a defect-#23 repro loop that was hammering the
machine with 20-second 1 GB-heap VM runs.  So this was contention, not an
arch difference.  Worth remembering as a harness rule: a package run and a
storm-repro loop on the same machine can cost the package run its results
without either one failing visibly.
