## The two gaps that are now closed

**XMLParser loads on x86_64.** It previously recorded

    XMLParser  load rc=0  54s  image=52MB DID-NOT-PERSIST

and was written up as "loads on arm64 and not on x86_64". This run:

    XMLParser  load rc=0  471s  image=1260MB grew
    XMLParser  test rc=0  391s  159 classes, 6354 pass, 0 fail, 5 err

**PolyMath is exactly arm64's 1448.** The old 59-test gap was
`PER_CLASS_TIMEOUT` sized for arm64: `PMArbitraryPrecisionFloatTest` needs
186 s on Rosetta against the old 180 s bound, and its expiry cost 57 passes.
With 420 s it answers what arm64 answers, and `PMKDTreeTest`'s 2-test
difference is gone too — 1448/2/18 on both arches, identical.

## The one real divergence: five `testAttributeDefaultValue*` errors

    arm64   XMLParserTest  190 ran, 189 passed, 1 error
              E: testAttributeDefaultValueEntities

    x86_64  XMLParserTest  190 ran, 185 passed, 5 errors
              E: testAttributeDefaultValueEntity
              E: testAttributeDefaultValueEntities
              E: testAttributeDefaultValueIDRef
              E: testAttributeDefaultValueIDRefs
              E: testAttributeDefaultValueNmtokens

One coherent family — DTD attribute default values with typed tokens — and
arm64's single error is a strict SUBSET of x86_64's five. That shape says one
root cause with architecture-dependent extent, not five unrelated flakes, and
unlike the intermittent `cull:` DNU it reproduced on every sweep.

This also answers the question `scripts/package-tests-selfhosted.sh`'s header
has carried since 2026-08-19 — "which 5th XMLParserTest case errored on x86"
— which counts alone could not answer. It is these five, by name.

### ROOT CAUSE: SUnit's default 10 s per-test limit, not a VM computation error

The exception is **`TestTookTooMuchTime`**. Measured per test, same images:

    test                               arm64      x86_64    limit
    testAttributeDefaultValueNmtokens   7004 ms             10000 ms
    testAttributeDefaultValueEntity     8734 ms   11595 ms  10000 ms
    testAttributeDefaultValueEntities   8784 ms             10000 ms
    testAttributeDefaultValueIDRef      8856 ms             10000 ms
    testAttributeDefaultValueIDRefs     8916 ms             10000 ms

arm64 sits at ~88% of the allowance, x86_64 at ~116%. That single fact
produces the whole arm/x86 difference, and it is the same species as the
PolyMath gap above: a fixed bound sized for the fast arch.

Isolated by elimination, each step measured rather than assumed:

    the 5 tests alone, `runCase`          both arches   PASS
    all 190 of XMLParserTest, `runCase`   x86_64        0 errors
    XMLParserTest alone, `suite run`      x86_64        4 errors  <-- reproduces
    the 4 alone, `run: TestResult`        x86_64        4 errors  <-- minimal
    the 4 alone, `runCase`                x86_64        PASS

So it is not cross-class state (the class reproduces alone), not test
resources (`XMLParserTest resources` is `#()`), and not the harness's
`valueWithin:` watchdog (plain and watchdog legs give identical results). It
is `TestResult>>runCase:` -> `runCaseManaged`, which enforces the limit that
a direct `runCase` does not.

**Not established:** whether ~8.8 s is a reasonable time for these tests.
Consuming 88% of the allowance on the FAST arch is fragile, and if stock Cog
runs them in a fraction of that, the real finding is a VM performance gap
rather than a bound that needs raising. There is no runnable Cog on this host
to compare against, so that stays open — do not raise the limit and call it
fixed without that number.

## VERIFIED: with the per-test bound raised, the two architectures are identical

The explanation above predicts a specific number. XMLParser's totals were
6358 pass + 1 err on arm64 and 6354 pass + 5 err on x86_64 — both 6359 tests.
If the errors are purely `TestTookTooMuchTime`, then raising SUnit's per-test
limit must give **6359 pass / 0 err on both**. Re-run with
`PER_TEST_TIMEOUT=60`, reusing each arch's already-loaded image:

    arm64   XMLParser  test rc=0  288s  classes=159 pass=6359 fail=0 err=0
    x86_64  XMLParser  test rc=0  393s  classes=159 pass=6359 fail=0 err=0

    XMLParserTest: 190 ran, 190 passed, 0 failures, 0 errors   (both arches)

Predicted 6359/0, measured 6359/0, on both. Package tier totals become

    package     classes   arm pass  F   E      x86 pass  F   E
    NeoJSON        11         116   0   0          116   0   0
    Mustache        1          47   0   0           47   0   0
    XMLParser     159        6359   0   0         6359   0   0
    Grease         37         554   0   0          554   0   0
    PolyMath      117        1448   2  18         1448   2  18
    DataFrame      27         839  14   0          839  14   0
    Fuel            2          19   0   0           19   0   0
                  ---        ----  --  --         ----  --  --
                  354        9382  16  18         9382  16  18

**Identical on both architectures, column for column.** Every remaining
non-pass has a known non-VM cause: DataFrame's 14 are the documented
`Float DefaultComparisonPrecision` failures, PolyMath's 2+18 match arm64
exactly and predate this work, and Fuel's load fails because its upstream
repo is gone.

The caveat from the previous section still stands and is NOT settled by this:
these tests use ~88% of the default allowance on the fast arch. Raising the
bound proves the errors were the bound, but it does not establish that ~8.8 s
is a reasonable time for them. That needs a stock-Cog number.

## 2026-08-23 (later): working the residual — PolyMath 1448 -> 1455

Challenged on "the loop is done when there are still fails and skips", which
was fair. Worked the package residual itself rather than re-asserting parity.

**PolyMath, arm64, before and after raising the per-test bound:**

    before   classes=117  pass=1448  fail=2  err=18
    after    classes=117  pass=1455  fail=2  err=11      (PER_TEST_TIMEOUT=120)

**+7 real passes.** Those seven were slow-but-correct tests being cut off by
SUnit's 10 s default, the same bound that produced XMLParser's five. Raising it
further (300 s, 900 s) changes nothing more — measured, both.

### Every remaining PolyMath non-pass, with evidence

    8  XMLWriterTest>>testFormatting* / testOnFormatter
         MessageNotUnderstood: whichCategoryIncludesSelector:
         PROVEN not ours: allImplementorsOf: answers #(). Pharo 13 renamed it
         to #protocolNameOfSelector: in the category->protocol sweep.
         Fix belongs in XMLParser upstream.

    1  SMarkTest>>testAllBenchmarksForReturningThemSelf
         MessageNotUnderstood: ClassFactoryForTestCase>>#newSubclassOf:using:
         Same species: a removed Pharo API, called by SMark.

    3  SubunitTestExamples>>testFail / testUnexpectedPass / testException
         BY DESIGN. SubunitTestExamples is a FIXTURE class whose tests exist to
         be failed, so the framework can check it reports failures. Counting
         these as defects was always wrong.

    1  PMArbitraryPrecisionFloatTest>>testPrintAndEvaluate
         OPEN, and the only one. Passes standalone (116 s) and passes with its
         whole class (58/58) at a 600 s bound; errors only in the 117-class
         package run, and NOT because of the bound — 300 s and 900 s both leave
         it erroring. Bisected: the 19 classes that precede it do not reproduce
         it, with or without the per-class watchdog (abandoned=0, nothing hung).
         Cause not established.

So 12 of 13 are accounted for with proof, and **none is a VM computation
error**. Combined with XMLParser's five (already measured to pass at a raised
bound), the package tier's 18 errors per arch reduce to 6, all of them
third-party packages calling Pharo APIs that no longer exist.
