arm64 run in `packages-arm-2026-08-22.md`, `build-x86/test_load_image` under
Rosetta, on an otherwise idle machine.

## The two gaps that are now closed

**XMLParser loads on x86_64.** It previously recorded

    XMLParser  load rc=0  54s  image=52MB DID-NOT-PERSIST

and was written up as "loads on arm64 and not on x86_64". This run:

    XMLParser  load rc=0  471s  image=1260MB grew
    XMLParser  test rc=0  391s  159 classes, 6354 pass, 0 fail, 5 err

**PolyMath is exactly arm64's 1448.** The old 59-test gap was
`PER_CLASS_TIMEOUT` sized for arm64: `PMArbitraryPrecisionFloatTest` needs
186 s on Rosetta against the old 180 s bound, and its expiry cost 57 passes.
With 420 s it answers what arm64 answers, and `PMKDTreeTest`'s 2-test
difference is gone too — 1448/2/18 on both arches, identical.

## The one real divergence: five `testAttributeDefaultValue*` errors

    arm64   XMLParserTest  190 ran, 189 passed, 1 error
              E: testAttributeDefaultValueEntities

    x86_64  XMLParserTest  190 ran, 185 passed, 5 errors
              E: testAttributeDefaultValueEntity
              E: testAttributeDefaultValueEntities
              E: testAttributeDefaultValueIDRef
              E: testAttributeDefaultValueIDRefs
              E: testAttributeDefaultValueNmtokens

One coherent family — DTD attribute default values with typed tokens — and
arm64's single error is a strict SUBSET of x86_64's five. That shape says one
root cause with architecture-dependent extent, not five unrelated flakes, and
unlike the intermittent `cull:` DNU it reproduced on every sweep.

This also answers the question `scripts/package-tests-selfhosted.sh`'s header
has carried since 2026-08-19 — "which 5th XMLParserTest case errored on x86"
— which counts alone could not answer. It is these five, by name.

### ROOT CAUSE: SUnit's default 10 s per-test limit, not a VM computation error

The exception is **`TestTookTooMuchTime`**. Measured per test, same images:

    test                               arm64      x86_64    limit
    testAttributeDefaultValueNmtokens   7004 ms             10000 ms
    testAttributeDefaultValueEntity     8734 ms   11595 ms  10000 ms
    testAttributeDefaultValueEntities   8784 ms             10000 ms
    testAttributeDefaultValueIDRef      8856 ms             10000 ms
    testAttributeDefaultValueIDRefs     8916 ms             10000 ms

arm64 sits at ~88% of the allowance, x86_64 at ~116%. That single fact
produces the whole arm/x86 difference, and it is the same species as the
PolyMath gap above: a fixed bound sized for the fast arch.

Isolated by elimination, each step measured rather than assumed:

    the 5 tests alone, `runCase`          both arches   PASS
    all 190 of XMLParserTest, `runCase`   x86_64        0 errors
    XMLParserTest alone, `suite run`      x86_64        4 errors  <-- reproduces
    the 4 alone, `run: TestResult`        x86_64        4 errors  <-- minimal
    the 4 alone, `runCase`                x86_64        PASS

So it is not cross-class state (the class reproduces alone), not test
resources (`XMLParserTest resources` is `#()`), and not the harness's
`valueWithin:` watchdog (plain and watchdog legs give identical results). It
is `TestResult>>runCase:` -> `runCaseManaged`, which enforces the limit that
a direct `runCase` does not.

**Not established:** whether ~8.8 s is a reasonable time for these tests.
Consuming 88% of the allowance on the FAST arch is fragile, and if stock Cog
runs them in a fraction of that, the real finding is a VM performance gap
rather than a bound that needs raising. There is no runnable Cog on this host
to compare against, so that stays open — do not raise the limit and call it
fixed without that number.
