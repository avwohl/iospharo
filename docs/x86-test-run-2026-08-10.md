**Why not spot.** `scripts/aws/config.env` sets `FORCE_ONDEMAND=1` with a
recorded reason: this account's spot capacity was reclaimed roughly every
10 minutes in June 2026, which destroys multi-hour SUnit runs. Spot is $0.27/h
against $0.69/h on-demand — about $2 over a full run — so this is a reliability
choice, not a cost one.

#### test_sista_ir — the one real failure

    FAIL: state.ip = state.method bytecodes_start + send bcOffset
    src/vm/jit/sista/test_sista_ir.cpp:1358

Established by direct comparison, not inference:

    arm64 macOS    exit 0, zero FAIL lines, on two separately-dated builds
    x86_64 Linux   exit 1, this single assertion, built today from jit HEAD

Both architectures reach the block (the preceding round-trips print on both);
on x86 the `--- round-trip bytecodeBase:` line that follows the check is never
printed, confirming the failure is in that block and not a stray earlier one.
The local arm binaries post-date the source file, so this is not a stale build.

Every other round-trip in the file passes on both architectures, and the other
JIT stub test (`test_asmjit_t1_stub`) passes on x86 — so this is narrow, not a
broadly broken x86 backend.

**Root cause — and it is not really a test problem.**

The Sista lowerer is split whole-file by architecture at CMake level, with no
`#if` inside either file, so the two implementations can drift silently. They
have:

    baked absolute bytecodeBase immediates   x86_64: 16    arm64: 0
    references to OFF_METHOD (state.method)  x86_64:  0    arm64: 2

arm64 hoists the bytecode base at function entry, recomputing it at runtime from
`state.method` (`methodObj + 16 + numLits*8 + startBcOffset`), then every deopt site
emits `add ipReg, bytecodesHoisted, #bcOffset`. The resulting ip is
method-relative and survives GC.

x86_64 instead bakes a compile-time constant at all 16 sites:

    uintptr_t addr = reinterpret_cast<uintptr_t>(bytecodeBase) + bcOffset;
    cc.mov(ipReg, Imm((uint64_t)addr));

and never loads `state.method` at all. `SistaLowering_x86_64.cpp:199` opts out
explicitly:

    (void)startBcOffset;  // jit-may22b Step 1: not yet supported on x86_64

This is drift, not a deliberate x86 design. Commit `7f2c55ce` ("jit-may22b Step 1
literal-patch: PROPER FIX ... GC-safe") added 16 lines to the arm64 lowerer and
4 to x86_64 — and those 4 are the opt-out above. Commit `8c3d1aa3` then updated
`test_sista_ir` to assert the new method-relative contract. The test encodes the
intended behaviour; x86 is the side that is wrong.

**Severity: this is not confined to the test.** Both production callers pass a
non-null `bytecodeBase` (`SistaRuntime.cpp:113` with `lifedBase`, and `:316`
with `bytecodes`), so on x86 every Sista-compiled method bakes the method
object's address into the code. The moment GC compaction or literal patching
relocates that method, the baked immediate is stale and a deopt sets `state.ip`
to a freed or reused address — the interpreter then resumes at that address.
That is precisely the failure `7f2c55ce` was written to eliminate on arm64.

A second divergence surfaced while tracing the same parameter: the multi-entry
dispatch prologue that consumes the hoisted base exists only on arm64
(`SistaLowering_arm64.cpp:371-393`); `dispatchableBlocks` has no occurrences in
the x86 lowerer. `SistaRuntime.cpp:118-124` nevertheless registers the compiled
function at every dispatchable bcOffset regardless of architecture, so on x86 an
entry at an interior loop-top offset lands in block 0 with un-materialised phi
inputs. That is reported here as observed-but-unverified: it follows from
reading the code, and unlike the ip bug it has no failing test pinning it.

> **FIXED 2026-08-11 in `ce2dcdd2`.** The arm64 hoist was ported to
> `SistaLowering_x86_64.cpp`: `OFF_METHOD` added, the bytecode base recomputed
> at fn entry from `state.method`, and all 16 baked sites routed through a
> single `emitSetIp()` helper (one materialisation point, so the two backends
> cannot drift apart the same way again). Verified on a native x86_64 box:
> `test_sista_ir` FAIL → PASS, `test_asmjit_t1_stub` and `test_class_table`
> unchanged, and a 192-class JIT-heavy SUnit subset at or below the pre-fix
> baseline's non-pass count over two runs. See "Validation and its limits"
> below — in particular, this fix does **not** resolve the weak-reference
> failures, contrary to what the first run suggested.

**Fix direction:** port the arm64 entry hoist to `SistaLowering_x86_64.cpp` —
load `state.method` (add `OFF_METHOD = 64`), decode `numLits` from slot 0
(`lsr 3`, `and 0x7FFF`), compute `methObj + 16 + numLits*8 + startBcOffset` into
a register once at entry, and replace all 16 baked `mov ipReg, Imm(addr)` sites
with `lea/add ipReg, [bytecodesHoisted + bcOffset]`. The arm64 implementation at
`SistaLowering_arm64.cpp:261-291` and `:1821-1837` is the reference.

This was root-caused by four independent investigations with adversarial
verification; the load-bearing claims (immediate counts, absent `OFF_METHOD`,
the opt-out line, both production call sites, and the commit's per-file line
counts) were then re-verified directly against the source and git history.

#### soccertheory's 12 errors are NOT a JIT bug

All 12 are one signature, and the Cog arm has zero errors:

    ERR STEptsFifaExampleTest>>testValidDocument
        (XMLFileException: File does not exist: soccerML.dtd (near line 2, column 40))

That is a missing *data file*, not miscompiled code. Our VM `chdir()`s to the
image's directory at startup; stock Cog resolves relative paths differently, so
a CWD-relative `soccerML.dtd` lookup succeeds under Cog and fails under ours.
The Cog log never mentions `soccerML.dtd` at all, consistent with it never
hitting the failing lookup.

This is still a real **compatibility** difference worth fixing — image-relative
vs process-CWD-relative file resolution is image-visible behaviour — but it
belongs in the file/path layer, not the JIT.

#### The one finding that correlates across suites: weak references

porpoise's single JIT-only failure is:

    FAIL PropertyManagerTest>>testPropertyManagerValueWeakness  [Got 1 instead of 2.]

A weak-reference test: passes under Cog (`pass=14 fail=0`), fails under ours.
That matches the SUnit result, where the only two clearly VM-level failures were
also weak-reference tests (`WeakOrderedCollectionTest` ×2, on garbage-collected
entries).

Three independent signals therefore land in GC/weak-reference territory on x86:

1. `test_sista_ir` — the x86 Sista deopt path bakes method addresses that go
   stale across GC (root-caused above, definitely real);
2. `WeakOrderedCollectionTest` ×2 in the SUnit suite;
3. `PropertyManagerTest>>testPropertyManagerValueWeakness` in porpoise.

Whether (2) and (3) share a root cause with (1) is **not established** — (1) is
about deopt resume addresses, while (2) and (3) are about weak-collection
semantics after collection. They may be unrelated. What is fair to say is that
the x86 GC interaction is the single most productive place to look next, and
that (1) is confirmed while (2) and (3) are observed-but-undiagnosed.

#### Timeout-only deltas: unresolved

The five timeout-only packages are **not** classified. The sweep ran 8 workers
on 16 vCPU, so a timeout can be contention rather than a hang, and the two arms
run sequentially within a worker rather than under identical load. Re-running
just those five with `WORKERS=1` would settle it; that was not done here because
the box was torn down. Treat them as unknown, not as regressions.

## Method notes

- The three suites were run **serially, not concurrently**. SUnit is
  non-differential and its scheduler preemption is wall-clock driven (a ~2 ms
  heartbeat), so running a parallel package sweep alongside it could perturb
  timing-sensitive tests and produce failures that are artifacts of load. The
  package sweep, being an A/B, does not have that problem.
- Each suite gets a **freshly fetched image**, never a reused one: image,
  changes and sources must come from the same fetch. A re-downloaded image next
  to a stale `.sources` previously produced garbage `sourceCode` and ~700 bogus
  AST/decompiler failures that mimicked a VM regression.
- `startup.st` is removed from the CWD before every prep and run. Pharo's
  `StartupPreferencesLoader` executes it from the current directory, and a
  leftover eval-mode `startup.st` silently hijacks the prep so the image saves
  without the SUnit runner.

## Validation and its limits (added 2026-08-11, after the fix)

The fix was validated on a second native x86_64 box against the pre-fix baseline
for the **same** 192 JIT-heavy classes (~6950 tests):

    baseline    6926 PASS   2 FAIL   3 TIMEOUT   0 ERROR
    with fix    6930 PASS   1 FAIL   0 TIMEOUT   0 ERROR    (run 1)
    with fix    6928 PASS   2 FAIL   0 TIMEOUT   1 ERROR    (run 2)

No regression: non-pass counts with the fix are at or below baseline. The
targeted defect is unambiguously fixed, because `test_sista_ir` is hermetic and
deterministic — FAIL before, PASS after.

**A correction worth recording.** After run 1 it looked like the fix had also
resolved the two `WeakOrderedCollectionTest` failures, which would have
retro-justified the "three signals in GC territory" hypothesis above. It had
not. Run 2 showed one of them failing again, and running that class in
isolation **with the fix** gave 3 FAIL / 1 PASS across four consecutive runs.
It is GC-timing dependent and flaky, independent of this change.

The same applies in reverse to `OpalCompilerTest>>testCompileSource`, which
failed once in run 1 and looked like a regression: it passed 4/4 in isolation
and did not recur in run 2.

The operative lesson is that **this harness has a noise floor of a few tests per
run**, so any single-run claim about an individual test — in either direction —
is unreliable. That also means the "12 genuine failures" list from the full
SUnit run above almost certainly contains flaky entries, and none of them should
be treated as a confirmed defect without repeat runs.

## Cost and teardown

The box ran ~4 h on-demand at ~$0.69/h, so roughly $2.80.

**Teardown completed and verified against the EC2 API**, not merely reported by
the script:

    i-0f55000ce8db8d3bd    terminated
    us-east-1              0 live instances
    us-east-2              0 live instances
    lease                  released
    security group / IAM role / GitHub deploy key    deleted

Four independent layers guarantee it does not survive:

1. explicit teardown at the end of this run;
2. the keep-alive lease goes stale ~30 min after heartbeats stop, and the
   `aws_watch` reaper terminates the box;
3. the on-box idle timer terminates after 30 min of process-idle;
4. the reaper's 12 h hard age cap as a runaway backstop.

The CPU-based CloudWatch idle alarm was deliberately **not** armed: it is
CPU-blind and false-kills low-CPU-but-active SUnit boxes, which is exactly this
workload. `provision.sh` defaults it off for that reason.

Note on the lease: `aws-lease-beat-hook.sh` resolves the box id from
`$AWS_LEASE_IID` or the EC2 DMI tag. Neither exists in a Claude session driving
the box from a Mac, so the hook exits without beating and the lease would have
gone stale mid-run. This run used an explicit bounded heartbeat (4 min interval,
6 h hard cap) to hold the lease exactly as long as the suites needed.
