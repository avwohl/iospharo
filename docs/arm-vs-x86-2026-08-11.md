# aarch64 vs x86_64 — full test comparison, 2026-08-11

Both architectures run natively on AWS against `jit`, using the same harness and
the same suites. The x86 run is `docs/x86-test-run-2026-08-10.md`; this document
is the comparison.

## What differed between the two runs

Recorded up front, because not all of it is neutral:

    box            x86: m6a.4xlarge (AMD EPYC, 16 vCPU)
                   arm: c7g.4xlarge (Graviton3, 16 vCPU)   — matched on vCPU
    lifecycle      both on-demand
    branch         x86: jit @ 37e6093e     arm: jit @ d31ae664
    stock Cog VM   x86: Pharo 10.3.9       arm: Pharo 10.2.1
    coverage       x86: 1889 of ~2052 classes (cut at 3h04m)
                   arm: 2052 classes, ran to completion in ~2h

Two of these matter for interpretation:

- **The arm run is on a later commit** — `d31ae664` includes the x86 Sista deopt
  fix landed after the x86 run. That fix only touches `SistaLowering_x86_64.cpp`,
  which is not compiled on arm, so it cannot affect these arm numbers. The rest
  of the delta is docs.
- **The stock Cog VM differs** (10.2.1 vs 10.3.9) because Pharo publishes no
  newer Linux-aarch64 VM. That VM only preps the image and provides the A arm of
  the package sweep; it is not the VM under test. It is still a real difference
  in the comparison's plumbing.

The x86 box also had two stray processes running during part of its SUnit
run (leftover evals from an unrelated probe). Load was low, but the x86 timing
numbers are not pristine.

## 2. SUnit

                        x86_64                  arm64
    classes             1889 (of ~2052)         2052  (complete)
    tests               26573                   27965
    PASS                26327                   27752
    FAIL                   11                      19
    ERROR                   1                       1
    TIMEOUT                73                      14
    SKIP                  161                     179
    pass rate           99.68%                  99.88%
    wall clock          3 h 04 m (cut)          2 h 02 m (complete)

Raw totals are not comparable — x86 never ran the last ~163 classes. The
per-test differential over the 26571 tests **both** runs executed is:

    WORSE on arm     4
    BETTER on arm   63
    arm-only      1394   (classes x86 never reached)

### The 63 "better on arm" are a speed story, not a correctness story

Nearly all are `x86=TIMEOUT -> arm=PASS`, and they cluster in exactly the
Spec/GUI families that stalled the x86 run: `StTranscriptPresenterTest`,
`StUnifiedProcessorTest`, `StWindowsProcessorTest`, `StThreadSafeTranscriptTest`,
`StTarjanAlgorithmTest`, `StSpotterTest`.

That is the same set the x86 run identified as its pathological tail — the one
whose collapse to ~13 classes/hour forced that run to be cut. On Graviton3 those
classes simply complete inside the per-test limit. Corroborating: arm finished
163 more classes in one hour *less* wall clock.

So the honest reading is that Graviton3 is meaningfully faster on this workload,
not that the VM is more correct on arm. A slower x86 box crossing a fixed
timeout threshold produces exactly this signature.

### The 4 "worse on arm" are within the noise floor

    ByteSymbolTest          testReadFromString                    x86=PASS arm=TIMEOUT
    SpJobListPresenterTest  testJobIsFinishedWhenWaiting...       x86=PASS arm=FAIL
    StSpotterModelTest      testAnnounceQueryEndedIsSentOnce      x86=PASS arm=FAIL
    StSpotterModelTest      testSpotterModelShouldWaitToPerform...x86=PASS arm=FAIL

All four are GUI/timing tests. The x86 work established this harness flips a few
tests per run in either direction (`WeakOrderedCollectionTest` gave 3 FAIL /
1 PASS across four identical isolated runs). Four differences out of 26571
comparable tests is at or below that floor. **Not** reported as arm defects —
they would need repeat runs to distinguish from flake, and those were not done.

### arm's 20 non-passes, grouped

    image hygiene (4)   ReleaseTest x4 — pristine-image assertions the harness's
                        own fileIn violates; also present on x86
    trait composition   OCClassBuilderTest ERROR — also present on x86
    GUI/debugger (8)    StDebugger x3, StDebuggerInspector, StFileBrowser,
                        StSpotter x3, SpJobListPresenter
    task kernel (3)     TKTBasicTask, TKTNewProcessTaskRunner, TKTTaskTimeout
                        — concurrency/timing; x86 never reached these classes
    environment (3)     ZnClientTest>>testQueryGoogle (needs internet),
                        ZdcPluginSSLSessionTest>>testCertificateName,
                        SystemDependenciesTest>>testExternalUIDependencies

The last group is not VM signal at all — `testQueryGoogle` reaches out to the
public internet. The `TKT*` failures are the only genuinely new information, and
they are in classes x86 never ran, so they are unclassified rather than
arm-specific.

Notably arm shows **no** `WeakOrderedCollectionTest` failures where x86 showed
two. Given that test is independently established as flaky, this is not evidence
of an architecture difference.

## 3. Package sweep (200-package A/B vs stock Cog)

**Not obtained on arm. The box terminated itself 74 minutes into the sweep and
all results were lost.**

CloudTrail records `TerminateInstances` at 2026-08-11T07:18:12Z, called by
`assumed-role/iospharo-arm-role/i-05fa7bff75e0eb0ad` from `18.188.242.254` —
the instance's own IAM role, from its own IP, via aws-cli on
`linux/aarch64/ubuntu.24`. That is `idle-shutdown.sh`, and `preserve.sh` ran one
second earlier, exactly as that script sequences it. Nothing was salvageable:
`preserve.sh` syncs notes and build logs, not `pkg200/` results.

Root cause, since fixed in `f034b896`: the idle check's "active process" pattern
listed `test_load_image` but **not `pharo`**. The sweep spends most of its wall
clock in Metacello package loads driven by the *stock* Cog VM, which is
network-bound — so no listed process was running and the 1-min load average sat
around 0.2, under the script's 0.5 floor. Thirty minutes of that and the box
declared itself idle and terminated, mid-run.

Worth noting the irony: this is precisely the failure the README documents for
the CPU-based CloudWatch alarm ("false-kills low-CPU-but-active SUnit boxes"),
which is why that alarm ships default-off. The process-based check was the safe
alternative and had the same hole.

So the arm-vs-x86 comparison covers the C++ binaries and the full SUnit suite,
but **not** the package sweep. The x86 sweep results stand alone in
`docs/x86-test-run-2026-08-10.md`; there is no arm counterpart to diff against.
Re-running it is ~1 h and ~$0.60 on a fresh box, and would now survive to
completion.

## Bottom line

On the evidence here the two architectures are **equivalent in correctness** at
the SUnit level: 4 differences worse on arm and 63 better, out of 26571
comparable tests, with the 63 explained by hardware speed against fixed timeouts
and the 4 inside the measured flake rate. No test failed on arm in a way that
implicates the VM and does not also fail on x86.

The one durable difference is throughput: arm completed the whole suite in two
thirds the wall clock while covering 9% more classes.

Scope limit, stated plainly: this conclusion rests on the SUnit suite and the
C++ binaries. The 200-package sweep was lost on arm (§3), so package-level
behaviour is compared for x86 only. Anything the sweep would have caught —
notably the CWD-relative file-resolution difference it surfaced on x86 — is
simply unmeasured on arm.

## Infrastructure defects this comparison exposed

Both were silent-success failures, and both are now fixed:

- `d1b0c1aa` — `x86-fullsuite.sh` hardcoded an x86-only stock-VM URL, so on
  aarch64 the download failed, the prep installed no SUnit runner, and the run
  reported `run exit=0` while producing an empty results file. It did this three
  times before being noticed. Now selects per architecture and fails loudly.
- `f034b896` — `idle-shutdown.sh` did not count `pharo` as an active process, so
  it terminated a box in the middle of a running sweep (§3).
