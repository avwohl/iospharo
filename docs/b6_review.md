# Adversarial review — B6 prim-111 `#class` inline plan

Verified against HEAD `124877dd`. Anchors in the plan all check out (insert point 4260-4263, j2jBail compares 5467-5470, else-branch 5541-5544, body 6745-6761, classifier area 21529, fill-path key derivation 21689-21699, stencil routing stencils.cpp:1576-1586). The two-fix premise (emit-side gap + classifier gap) is correct and confirmed in source. Findings below, worst first.

## F1. HIGH — pk=24 aliases the W6 even/odd flag bit (bit 51): wrong results under PHARO_T1_INLINE_EVEN_ODD, silent perf kill for heap receivers

The extras encodings overlap: pk=24 = 0b11000 << 48 sets **bits 52 AND 51**. Bit 51 is simultaneously the W6 even/odd spec FLAG (write side Interpreter.cpp:21201-21206 / 21830-21833; dispatch side AsmjitT1.cpp:4213-4216 `tbnz x7,#51,tryEvenOdd`, emitted for nArgs==0 under `PHARO_T1_INLINE_EVEN_ODD`). The W6 tbnz sits at 4214 — BEFORE the heap tst at 4217 and BEFORE Edit 1's insert point at 4263. Dispatch order does not protect you.

Failure scenarios (the second exists TODAY and Edit 2 floods it):
- Heap receiver, EVEN_ODD=1: every pk=24 entry is stolen by `tbnz #51` → tryEvenOdd → SmI tag check fails (6072-6074) → dispatchCached. Correct but the entire B6 win silently evaporates under exactly the knob-bisect workflow CLAUDE.md prescribes for JIT Heisenbugs — a bisect would conclude "EVEN_ODD changes class-send timing," pure noise.
- Immediate receiver (`5 class`), EVEN_ODD=1: cold-fill ALREADY writes pk=24 on immediate-keyed entries today (the pk block at 21240-21243 is `extra == 0`-gated but NOT heap-gated), and Edit 2 mass-produces them. tbnz#51 fires, tryEvenOdd's SmI check PASSES, kind = extras bit 48 = 0 → returns `true`/`false`. **`5 class` evaluates to a Boolean.** No crash, no log.

Note pk 9-15 also set bit 51, but only at nArgs==1 sites where the W6 test isn't emitted; pk=24 is the FIRST 0-arg pk with bit 51 set, so this plan is what makes the collision live.

Fix (root cause, small): the single-bit tbnz is an unsound discriminator. Make the W6 dispatch decode the full field: W6 entries are exactly field∈{8,9} (`lsr x6,x7,#48; and x6,#0x1F; cmp #8; b_eq; cmp #9; b_eq` — 2 extra instrs under an opt-in knob), OR emit the pk-24/20/16 compares BEFORE the bit-51 tbnz (the pre-bit-60 pk block at 4137-4178 is the house precedent: pk compares always precede W tests) with a 2-instruction tag guard at the top of each body. Either way, add `PHARO_T1_INLINE_EVEN_ODD=1` (and the other W knobs) to the validation-ladder A/B matrix.

## F2. HIGH — Edit 5's insertion position is underspecified, and the safe window is exactly 11 lines wide

"After the bit-58/54 pre-split dispatches, before the tst at 4217" spans the bit-53 (4206), bit-52 (4210), and bit-51 (4214) tbnz tests. If the pk-24 compare lands after 4214, F1's wrong-Boolean case applies to 1b even though Edit 5 was specifically built for immediates. If it accidentally lands after the tst, immediates never reach it and 1b is silently dead (class= counts heap only — validation step 2 would still "pass" on the heap loop). Fix: specify the insert as immediately after the bit-54 dispatch (line 4202), i.e., before bits 53/52/51; bits 53/52 are nArgs==1-only so the binding constraint is "before the bit-51 tbnz". Add the polymorphic-immediate eval smoke as a REQUIRED gate (it is in the ladder — good — but tie it to nonzero class= delta, not just correct output).

## F3. MED — Edit 2 classifies pk=24 by primitive index only; 1-arg prim-111 methods exist and mean "class of the ARGUMENT"

`primitiveClass` reads `stackValue(0)` (Primitives.cpp:2959-2973): for argCount 0 that's the receiver, for argCount 1 it's the mirror-style argument (Pharo binds prim 111 to `MirrorPrimitives`-style `classOf:` too). Edit 2 keys off `primIdx == 111` with no arity check, so a 1-arg site gets pk=24 extras whose inline semantics (class-of-receiver) are WRONG for that site. Today you're saved only by emit-side `nArgs == 0` gates (4260 insert, 5458, 5532) — but the stencil tier decodes pk at runtime with arbitrary nArgs (stencils.cpp:1576), where pre-Edit-3 it misroutes to RT_NEW_PRIM and post-Edit-3 it merely goes slow. Defense-in-depth is one `sendArgCount == 0` term away. Fix: add `sendArgCount == 0` to Edit 2's condition (and to the prim-75 companion). The cold-fill writer at 21240-21243 has the same latent hole — pre-existing, note in risk list.

## F4. MED — Edit 3 as specified still routes the bit-identical W3 aliases into RT_NEW_PRIM

`tightening primKind >= 17` to `== 17 || == 18` does not help the encoding that is genuinely ambiguous: W3 IntArithReturn kind 1/2 (`bit 52 | 1..2 << 48`, written by DEFAULT at 21195-21200 / 21826-21829 — detection in detectTrivialMethod is NOT knob-gated, only the T1 tbnz consumer is) is bit-for-bit identical to pk 17/18. At a stencil-tier 1-arg site, a `^ self - arg`-shaped callee's entry decodes as pk 17 → RT_NEW_PRIM reads the (non-class) receiver's slot 2 as a format word. The only disambiguator available is arity: pk17 is only meaningful at 0-arg sites, pk18 at 1-arg, W3 only at 1-arg. Fix: make Edit 3 also check nArgs (`(primKind == 17 && nArgs == 0) || (primKind == 18 && nArgs == 1)`), which closes both the pk-19..24 misroute the plan targets AND the W3-kind-1 alias (kind 2 vs pk18 at 1-arg remains ambiguous — pre-existing, only fixable by excluding bit-53/54-style W discrimination at write time; flag for a follow-up). Also note Edit 3 serves x86_64 and arm64 both — good — but the jit-x86 branch merge note (risk #8) should include it explicitly.

## F5. LOW/MED — the noteLateSpecBit mirror in Edit 2 is a no-op as designed

`JITRuntime::noteLateSpecBit` (JITRuntime.cpp:587-636) weights only bits 59/57/58/60; `newExtra = 24<<48` gets weight 0 and returns at 616. The plan's "so tier-2 recompile picks it up" does nothing. It also doesn't NEED to: T1 send sites read extras at runtime (compares are emitted unconditionally at every 0-arg site), and tier-2 stencil sites decode extras at runtime too. Fix: drop the hook and the claim (or extend the weight table only if a pk-specialized stencil ever exists). Keeping a dead hook invites someone to "fix" the weight table later and trigger recompile waves.

The one residual: the j2jBail-origin compares carry the documented partial-state-commit suspicion (4228-4242 comment: "state.ip = callee bcStart … before a late bail") — but pk-only entries never have bit 60, so the new traffic uses ONLY the clean fall-through origin; exposure unchanged. Keep plan risk #9's comment requirement.
- **GC.** Vector storage malloc'd, resized exactly once (ObjectMemory.cpp:111-115), base captured in g_classTableBase; entries rewritten at scavenge root-visit (1657) and compaction (3648); snippet is straight-line (no safepoint) and loads base+entry fresh per send. The weak-at-mark table entry semantics are identical to interpreter classOf — no new exposure. Edit 4 aliases stay current via the forEachMemoryRoot walk (ObjectMemory.hpp:1008-1014) since all three classes are strongly held elsewhere.
- **Immediates mapping.** Tags 1/3/5 are the only immediate tags; `and #7` / `tst #7` / `0x1F` / ClassIndexMask are all valid AArch64 bitmask immediates (contiguous) — no asmjit silent-drop exposure. - **Metaclass/class receivers.** A class receiver's header classIndex IS its metaclass's table index; the snippet computes exactly what `classOf` computes (ObjectMemory.cpp:450-451) — byte-equivalent for classes, metaclasses, anything heap. Megamorphism at class-heavy sites (each metaclass = distinct key) is a fill-rate matter, not correctness.
- **Forwarders/become.** This VM has ZERO `followForwarded` in Interpreter.cpp — become is EAGER (`scanStackReplace` Primitives.cpp:9348+, `becomeForward` allObjectsDo ObjectMemory.cpp:1383-1427), so no mutator-visible forwarders exist on the stack; a key can never be ForwardedClassIndex(8) at fill time. `primitiveClass`'s followForwarded is dead belt-and-suspenders. - **Extras-bit budget vs W1/W2 (bits 54/53).** The 0x1F mask covers bits 48-52 only; pk values can never set 53/54, and W1/W2 payloads (1-7, 0-5 in bits 48-50) can't equal 16/20/24, so Edit 1's three compares are false-match-free. The budget problem is exclusively F1's bit-51/52 flag aliasing.
