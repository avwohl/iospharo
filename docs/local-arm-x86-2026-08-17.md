# Running both architectures on one machine — 2026-08-17

Until now the arm-vs-x86 comparison needed two AWS boxes, which is why the
2026-08-11 run has the caveats it does: different instance types, different
stock Cog VMs, an x86 run cut at 3 h and an arm package sweep lost to an
idle-shutdown. This machine (Apple M4, arm64, macOS 27) runs both natively
enough to remove most of that.

## Both binaries build and run here

    arm64   cmake -S . -B build-rel -DCMAKE_BUILD_TYPE=Release
    x86_64  cmake -S . -B build-x86 -DCMAKE_BUILD_TYPE=Release \
                  -DCMAKE_OSX_ARCHITECTURES=x86_64

The x86_64 build is clean and runs under Rosetta. Verified it executes real
Smalltalk rather than merely starting: `3 factorial` = 6 and `100 factorial`
has 158 digits. Both xcframeworks ship a `macos-arm64_x86_64` slice, and the
JIT already has `Tier2Compiler_x86_64.cpp` and `generated_stencils_x86_64.hpp`,
so nothing needed porting.

`scripts/sunit-sweep.sh` takes the VM binary as an argument precisely so the
same suite can be run against both from one place.

## What the stock Cog VM cannot do here

`scratchpad/pharo/pharo-vm/Pharo.app` aborts on this host:

    Could not allocate codeZone in the expected place (0x320000000),
    got 0x7000000000

That is the macOS ASLR problem this project exists to solve, so on this machine
there is no reference VM to A/B against. Anything that needs "does Cog do this
too?" still needs a Linux box. Comparisons here are ours-vs-ours across
architectures, which is still worth having — it is what catches codegen
divergence.

## Two harness facts that cost time

**`eval --save` does not persist under `test_load_image`.** Several docs
describe prepping an image with `pharo image eval --save "..."`. That is the
stock Cog VM's flag; ours forwards it to the image's command-line handler and
nothing is written. Verified by setting a global and finding it gone on the
next launch. Use an explicit snapshot instead:

    <vm> fresh.image eval "'...run_sunit_tests.st' asFileReference fileIn.
                           Smalltalk snapshot: true andQuit: true"

A correctly prepped Pharo 13 image goes from ~52 MB to ~74 MB and answers
non-nil for `Smalltalk at: #SUnitRunner`.

**The suite must be run on an idle machine, and the failure mode is
misleading.** Running the sweep while `cmake --build -j4` was compiling
produced a scatter of `MessageNotUnderstood` and `Improper store into indexable
object` errors, dropping the apparent rate from 99.7% to 96.8% — in classes
that score 100% in isolation. It looks exactly like a regression against the
last recorded run, and it is not one. Measured, same batch, three consecutive
idle runs:

    batch 1-50   772/774 PASS   0 FAIL   0 ERROR   (identical all three times)

Competing load does not slow a wall-clock watchdog down evenly; it converts
passes into ERRORs. If a result looks like a regression, re-run it idle before
believing it.
