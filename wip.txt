## Current State: ForceYield Fixed, 2 Deterministic DNUs Remain

### Summary
Fixed the main source of non-deterministic DNUs: forceYield was preempting to LOWER-priority processes, violating Smalltalk scheduling invariants. Changed to same-priority round-robin only (matching standard VM behavior).

### DNU counts (after fix)
- Non-deterministic DNUs: 0-2 per run (was 3-19)
- Deterministic DNUs: 2 per run (handled by exception system, not crashes)
- 4/10 runs had ZERO non-deterministic DNUs

### Changes Made (committed)
1. **forceYield same-priority only** — only yield to processes at the SAME priority (round-robin time-slicing). The old code yielded to LOWER priority, which violated scheduling invariants and caused state corruption during process switches.
2. **numTemps fix in pushFrame()** — push `numTemps - argCount` nil slots instead of `numTemps`, since the header's numTemps field includes args.
3. **Enhanced DNU logging** — sender chain dump at fd=0, full frame trace for specific selectors.

### Deterministic DNUs (not bugs, handled by exception system)
1. **`#handleClassChange:` on ByteSymbol** (step ~1592684, fd=43)
   - During class change announcement delivery in startup
   - A subscription handler receives a ByteSymbol instead of a class
   - Caught by `on:do:` exception handlers
   - Likely an image-side issue with stale class change subscriptions

2. **`#printStringHex` on UndefinedObject** (step ~1793629, fd=26)
   - In Epicea changelog system during `nextSuffix`
   - A counter/ID is nil, causing `printStringHex` to fail
   - Caught by exception handlers
   - Related to uninitialized Epicea store on fresh startup

### Remaining Non-Deterministic DNUs (0-2 per run)
- Occasional `#nextPut:` on nil, `#findNextUnwindContextUpTo:` on wrong type
- From timer semaphore signaling, not from forceYield
- Related to how semaphore signal triggers `resume:through:` context walks

### Key Insight
The standard OpenSmalltalk VM NEVER preempts to lower-priority processes. Lower-priority processes only run when all higher-priority processes are voluntarily waiting. The forceYield mechanism should ONLY do same-priority round-robin time-slicing.

### Next Steps
1. **Investigate timer semaphore DNUs** — the remaining 0-2 non-deterministic DNUs come from semaphore signaling (processPendingSignals → signal → resume → executeFromContext). The context chain may have stale entries after process termination.
2. **Consider ignoring deterministic DNUs** — they're caught by exception handlers and don't affect functionality. Could suppress logging for known-handled cases.
3. **Test with full app** — build and run Mac Catalyst to verify UI rendering works with process switching fixed.
