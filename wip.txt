## Current State: Investigating Non-Deterministic DNUs from Process Switching

### Key Finding
DNUs are caused by the forceYield process switching mechanism (transferTo/materializeFrameStack/executeFromContext round-trip).

**Proof:** Disabling forceYield reduces DNUs from ~4/run to ~0/run (0,0,0,2,0 across 5 runs).

### DNU counts
- With forceYield enabled: ~3-8 per run, non-deterministic (different selectors each time)
- With forceYield disabled: 0-2 per run (rare `findNextUnwindContextUpTo:` from timer semaphore signaling)
- Common DNUs: `#adaptToNumber:andSend:` on nil, `#findNextUnwindContextUpTo:` on nil, `#<unknown>` selector, `#beingWaitedOn` on nil, various nil receivers

### Changes Made (uncommitted in Interpreter.cpp)
1. **numTemps fix in pushFrame()** — standard VM pushes `numTemps - numArgs` nils (not `numTemps`). Fixed but didn't change DNU count. Still correct per standard VM behavior. **Currently REVERTED** — needs to be re-applied.
2. **DNU logging improvement** — all DNUs now show calling method + frame stack (not just ensure:/runStepMethods)

### Root Cause Analysis
The forceYield mechanism triggers `transferTo()` which:
1. Calls `materializeFrameStack()` — saves inline frames as Context objects
2. Stores top context to old process's suspendedContext
3. Calls `executeFromContext()` on new process's suspended context

Something in this round-trip corrupts state. The non-determinism is because forceYield fires at different bytecode positions each run (every ~1000ms from heartbeat timer).

### Next Steps
1. **Re-apply numTemps fix** — change `for (int i = 0; i < numTemps; ++i)` to `for (int i = 0; i < numTemps - numArgs; ++i)` in pushFrame() line ~13353
2. **Investigate materializeFrameStack/executeFromContext round-trip** — the bug is somewhere in how frames are saved to contexts and restored. Key areas:
   - Expression stack calculation in materializeFrameStack (exprStart/exprEndPtr)
   - Context restore in executeFromContext (stackp vs numTemps handling)
   - Whether sender chains are properly maintained through save/restore
3. **Check returnValue at frameDepth_=0** — after executeFromContext restores a single context, returns need to walk the sender chain via activeContext_. Verify this works correctly.
4. **Consider:** The standard OpenSmalltalk VM frame layout has saved IP, FP, method, context, flags ON the stack. Our VM uses C-side savedFrames_[]. This fundamental difference means materializeFrameStack must correctly reconstruct what the standard VM would have stored.
