Record

  • Defect: sameThreadCallbackEnter calls ptEnterInterpreterFromCallback on the thread that made the callback. When that thread is not the VM thread, two threads run the interpreter, and the VM stops with a segmentation fault. The image has TFUFFICallbackTest>>testCallbacksInOtherThread set to skip for this runner, with that cause in a remark.
  • Change, first commit: for a callback from another thread, the calling thread waits on a platform semaphore. callbackFrontend already puts each invocation in the queue of pending callbacks, so the image runs the callback in the VM thread. sameThreadCallbackExit gives the signal. The worker runner does the same for a thread that is not its own.
  • Change, second commit, from a review of the first:
    • A lock for the callback stack of a runner. callbackFrontend pushed with no lock from any thread, and primitiveCallbackReturn tested and popped in two steps. The worker runner had the same exposure.
    • The runner keeps the VM thread as a pthread_t from primitiveGetSameThreadRunnerAddress. ioVMThread is set only in a build with PHARO_VM_IN_WORKER_THREAD, and on Windows its type cannot hold a pthread_t.
  • Test (2026-11-17, macOS 27, arm64, the stock app with the core library of the changed build): the 14 tests of TFUFFICallbackTest pass, 8 runs of 8. testCallbacksInOtherThread passes for the same-thread runner and for the worker runner. On the stock VM the same-thread case stops the VM, so the test skips there.
  • Not tested: Windows and Linux, and two threads that call back at the same time.
  • The image side: scripts/image-fixes/30-ffi-callback-from-other-thread.st keeps the skip only for a VM without the change. Our VM always ran such a callback in the VM thread.

VM thread works as before.

From: Aaron Wohl

Subject: [PATCH 2/2] FFI callbacks: a lock for the callback stack; the
 same-thread runner keeps its own VM thread id

Two defects of the change before this one, found by a review:

- callbackFrontend pushed on the callback stack of the runner with no lock,
  from any thread, and primitiveCallbackReturn tested and popped the stack
  in two steps.  A push from another thread between the two steps lost an
  invocation, and its callback then never returned.  The push and the put
  in the queue of pending callbacks also were two steps, so two threads
  could give the image an order that was not the order of the stack.  The
  worker runner had the same exposure.  A lock now makes each pair one step.

- The same-thread runner asked ioVMThread for the VM thread.  That variable
  is set only in a build with PHARO_VM_IN_WORKER_THREAD, and on Windows its
  type cannot hold a pthread_t.  The runner now keeps the thread of
  primitiveGetSameThreadRunnerAddress and compares with pthread_equal, as
  the worker runner does.
