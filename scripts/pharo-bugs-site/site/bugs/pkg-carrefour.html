"moosetechnology/Carrefour (v6), Pharo 14.  Carrefour was written against a Moose image
of 2023.  The Famix of Pharo 14 (branch development) changed in five ways that the package
code and the test data of Carrefour do not follow.  Each entry below repairs one of them
where the defect is.

Defect A (old names of the Moose query API; entries 1 to 4).  Famix dropped atScope:,
allAtScope:, allToScope:, toScope:, atAnyScope:, allAtAnyScope:, allToAnyScope:,
allParents, children, queryAllOutgoingInvocations and the like, and keeps them only in the
package Famix-Deprecated, which the load does not bring in.  A load of Famix-Deprecated would
not help: each deprecated method signals a Deprecation, and the runner of the tests counts a
Deprecation that reaches a test as an error.  So the callers get the current names.  The same
defect is in three places: Carrefour (the binder, two extensions, five tests), FAMIX2Java (the
exporter, a dependency of Carrefour-Exporter), and FAST v2 (a dependency through FAST-Java
v3.0.9).

Defect B (test data; entry 0).  The test data of Carrefour is a JSON model in the Famix Java
metamodel of 2023, and the setUp of every test class below CRFTest imports it with
importFromJSONStream:.  Four things in the model of 2023 are gone from the metamodel of Famix
development.  (1) ParameterType and ParameterConcretization elements: the metamodel has
TypeParameter, and a Concretization that hangs on a parametric association.  The text of the
fixture changes ParameterType to TypeParameter, genericParameters to typeParameters, drops the
5 old Concretization and ParameterConcretization elements, and makes the two concrete
ParametricInterface elements (Map and Comparable) plain Interface elements with the same id and
name.  (2) referredType of a Reference is now referredEntity (59 elements).  (3) declaredType of
a Method, Attribute, Parameter or LocalVariable (84 elements) is no longer a property: the
declared type is now the declaredType of a separate EntityTyping element that the typed entity
points to with its property typing.  The Fame importer does not fail on an unknown property, it
keeps the value as a plain attribute, so the 84 types were silently lost and
CRFBindingMethodWithTypeParameter>>testBindTypeParameter got nil for the declared type of the
method.  The entry adds one EntityTyping element for each of the 84 and sets typing.  (4) variable
of an Access is now candidates (38 elements), and the 38 accesses had no variable.  The
properties of every element of the new text were checked against the properties of the metamodel
of the image, and no unknown property is left.

Defect C (Famix; entry 5).  FamixJavaMethod>>isConstructor of Famix development answers
false for every method, also for a method with the kind #constructor that the importers set
(25 methods in the test data).  The older Famix answered #constructor = kind, and
FamixJavaInitializer, a subclass, still computes the answer.  The binder of Carrefour sends
isConstructor to the candidate of each invocation, and so it bound no constructor call to a
'new' expression: 9 tests ended with Got nil instead of a FASTJavaNewExpression or a
FamixJavaInvocation.  The entry answers the kind again.

Defect D (test code; entry 6).  CRFExporterTest sends declaredType: to a FamixJavaMethod, a
setter that Famix removed together with the property.  The method now has only the getter
(typing declaredType).  The two tests give the method a typing: FamixJavaEntityTyping new
declaredType: primitiveInt.  The expected Java text does not change.

Defect E (test code; entry 7).  The tests look up a Famix entity by the name of its mooseName
with the separator '::' between the package and the class (hello::Hello.returnNumber(int).i).
Famix 'replaced :: by . in mooseName', so the name is hello.Hello.returnNumber(int).i.  The
three tests (testUsagesOfParameterI, testUsagesOfReturnI, the setUp of
CRFRemoveReferencesStaticTest) get the new separator.  They look for the same entity.

The load itself needs a change of the manifest row: Carrefour needs the Famix Java metamodel
(Famix-Java-Entities and Famix-Java-Generator) and the package TinyLogger, and the baseline of
FAST-Java v3.0.9 does not bring them in.  The file here does not change the load.

fixes/moosetechnology-fast-java.st for FAST v3 (row 76); this row loads FAST v2.

Entry 3 (rewrite of the old names in the methods of the packages Carrefour-*, Famix2Java and
