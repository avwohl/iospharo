Record

  • Defects, measured on stock Cog v12.0.6 (macOS arm64, 2026-11-17) with scripts/cogdiff/newfile_plugin_checks.st and scripts/cogdiff/newfile_plugin_ours_checks.st:
    • A read of 3 bytes into a ByteArray of 2 bytes answers 3. The read and write primitives do not check the buffer, so the plugin writes past the object.
    • A read into an Array answers 2. The plugin writes bytes into pointer slots.
    • A read into a read-only ByteArray answers 2.
    • A copy of the handle of a closed file, given to the close primitive, stops the VM with Abort trap: 6. The handle holds a C pointer, and the plugin frees the pointer a second time.
  • Defects that the sources show (not measured on stock Cog):
    • NewFile_memoryUnmap (unix) tests the reference count the wrong way round. It unmaps while references remain, and never at the last one.
    • A second memory map after the file changed size answers the old mapping. The image gives the view the new size.
    • A read-write map after a read-only map of the same file answers the read-only mapping.
    • NewDirectory_open (unix) gives opendir() the path of the image, which has no terminating NUL.
    • NewFile_seek (unix) uses a NULL handle.
  • Change, in two commits:
    • Slang (NewFilePlugin.class.st): the four read and write primitives check the buffer (a byte or word object, the range in bytes, and no read into a read-only object). A handle must be a byte object of the size of a pointer. The primitives that allocate read their arguments again after the allocation.
    • C (UnixFile.c, Win32File.c, new NewFileHandles.h): a handle holds a token from a counter that never repeats, and a table has the live tokens. A token that is not live acts as a NULL handle. The map and unmap defects and the two NULL and NUL defects are repaired.
  • Test (2026-11-17, macOS 27, arm64, the Cog build with the change):
    • scripts/cogdiff/newfile_plugin_checks.st: the 36 lines are the lines of our VM. The three reads above fail the primitive.
    • scripts/cogdiff/newfile_plugin_ours_checks.st: no stop of the VM. A copy of the handle of a closed file does nothing (the answer of the stock plugin for a NULL handle). A second map after the file grew, and a read-write map after a read-only map, answer no mapping.
    • The 42 tests of the package ronsaldo/pharo-newfile pass.
    • A full sweep of the Pharo 14 tests on the Cog with the change (sweepcogp14-new8, 39461 tests) has the same result as the sweep before the change.
  • Not tested: Windows (the Windows sources have the same changes, and they were not compiled) and Linux.

cog-newfile-plugin-buffer-and-handle-checks.patch (download)
From b76510a5b3f680ffcbbe8424683b3a1fda2727e9 Mon Sep 17 00:00:00 2001
From: Aaron Wohl
Date: Tue, 17 Nov 2026 13:42:21 -0500
Subject: [PATCH 1/2] NewFilePlugin: check the buffer and the handle objects in
 the primitives

The read and write primitives (primitiveFileReadInto,
primitiveFileReadIntoAtFileOffset, primitiveFileWriteFrom,
primitiveFileWriteFromAtFileOffset) gave the address of the buffer to C
without a check.  Measured on stock Cog v12.0.6 (macOS arm64):
 - a read of 3 bytes into a ByteArray of 2 bytes answers 3 (the plugin
   writes past the buffer);
 - a read into an Array answers 2 (the plugin writes bytes into pointer
   slots);
 - a read into a read-only ByteArray answers 2.

The primitives now call checkBuffer:offset:size:forRead:.  The buffer must
be a data object without pointers (isWordsOrBytes:, so not an Array and not
a CompiledMethod), offset + size must not be more than byteSizeOf: the
buffer (written so that it cannot overflow), and a buffer for a read must
not be immutable.  Otherwise the primitive fails with PrimErrBadArgument,
PrimErrBadIndex or PrimErrNoModification, before any C call.

The handle objects (ExternalAddress) were read with firstIndexableField:
without a check, so a SmallInteger or a short object gave a wild read.
handleValueOf: now fails the primitive unless the handle is a byte object of
BytesPerWord bytes.

primitiveFileOpen, primitiveDirectoryOpen, primitiveDirectoryNext and
primitiveMemoryMapWithProtection allocated an ExternalAddress and then used
oops (path, handle) that were read before the allocation, which can move
young objects.  They now read the path and the handle after the allocation,
and do nothing when the allocation failed.

From: Aaron Wohl
Date: Tue, 17 Nov 2026 13:42:21 -0500
Subject: [PATCH 2/2] NewFilePlugin: handle tokens instead of C pointers, and
 repairs in the C library

The ExternalAddress that the image holds contained the C pointer of the
NewFile_t or NewDirectory_t, and each call dereferenced and the close call
freed whatever pointer the image gave back.  Measured on stock Cog v12.0.6
(macOS arm64): the copy of the handle of a closed file, given to
primitiveFileClose, stops the VM with "Abort trap: 6" (free of the same
pointer twice).  A copy of a closed handle can also meet a later file at the
same address.

New include/common/NewFileHandles.h: a table of live handles.  The value
that NewFile_open and NewDirectory_open answer is now a token from a counter
that never repeats in the process; every function looks the token up (with
its kind, file or directory) and a token that is not live is handled like a
NULL handle (close, rewind, unmap do nothing; read, write, size answer -1,
tell answers 0, truncate answers false, next answers NULL).  A stale token
can never match a later file.  The table is sorted by token (binary search)
and is used from the VM thread only.

Other defects repaired in the same files:
 - unix NewFile_memoryUnmap tested the count the wrong way round: it called
   munmap while references remained and never at the last one.  Now it
   unmaps at the last reference.
 - unix and win NewFile_memoryMap: a second map after the file changed size
   answered the old mapping, and the image gave the view the new size.  Now
   it answers NULL (no mapping) when the file size is not the mapped size.
 - a read-write map after a read-only map of the same file answered the
   read-only mapping.  Now it answers NULL; a read-only map after a
   read-write map still shares the mapping.
 - unix NewDirectory_open gave opendir() the path of the image without a
   terminating NUL; it now uses the NUL-terminated copy.
 - unix NewFile_seek dereferenced a NULL handle (a closed file); it now does
   nothing.
 - win NewFile_preparePath used strlen() on the path of the image, which has
   no NUL: it now uses the given size.
 - win NewFile_seek called abort() for an unknown seek mode, which stops the
   VM on bad input from the image: it now does nothing.
 - the result of malloc/calloc is checked.

The Windows sources are not compiled on this machine; they were checked with
clang -fsyntax-only against a stub windows.h only.

+#ifndef PHARO_NEWFILE_HANDLES_H
+#define PHARO_NEWFILE_HANDLES_H
+
+/*
+ * Table of the live file and directory handles.
+ *
+ * The image keeps the value that NewFile_open and NewDirectory_open answer
+ * in an ExternalAddress, and gives the value back with every later call.  The
+ * value is therefore input from the image.  It is not a C pointer: it is a
+ * token from a counter that never gives the same token twice in one process.
+ * Each call looks the token up in this table.  A token that is not in the
+ * table (a copy of the handle of a file that is closed, a handle of the wrong
+ * kind, a random number) finds no object, and the call fails as for a NULL
+ * handle.  Nothing is dereferenced or freed on the word of the image.
+ *
+ * The VM calls the plugin primitives from the VM thread only, so the table has
+ * no lock.
+ *
+ * The functions are static, so each source file of the plugin has its own copy
+ * of the table; a platform build compiles one of UnixFile.c and Win32File.c.
+ */
+
+#include <stddef.h>
+#include <stdint.h>
+#include <stdlib.h>
+#include <string.h>
+
+typedef enum NewFileHandleKind_e
+{
+    NewFileHandleKindFile = 1,
+    NewFileHandleKindDirectory,
+} NewFileHandleKind_t;
+
+typedef struct NewFileHandleEntry_s
+{
+    uintptr_t token;
+    int kind;
+    void *object;
+} NewFileHandleEntry_t;
+
+/* The entries are sorted by token, because tokens only grow. */
+static NewFileHandleEntry_t *NewFileHandles_entries = NULL;
+static size_t NewFileHandles_count = 0;
+static size_t NewFileHandles_capacity = 0;
+static uintptr_t NewFileHandles_lastToken = 0;
+
+/* Answer the index of the entry of the token, or -1. */
+static ptrdiff_t
+NewFileHandles_find(uintptr_t token)
+{
+    size_t low = 0, high = NewFileHandles_count;
+    while(low < high)
+    {
+        size_t middle = low + (high - low) / 2;
+        uintptr_t middleToken = NewFileHandles_entries[middle].token;
+        if(middleToken == token)
+            return (ptrdiff_t)middle;
+        if(middleToken < token)
+            low = middle + 1;
+        else
+            high = middle;
+    }
+    return -1;
+}
+
+/* Answer a new token for the object, or NULL when there is no memory or no token left. */
+static void *
+NewFileHandles_register(int kind, void *object)
+{
+    if(!object || NewFileHandles_lastToken == UINTPTR_MAX)
+        return NULL;
+
+    if(NewFileHandles_count == NewFileHandles_capacity)
+    {
+        size_t newCapacity = NewFileHandles_capacity ? NewFileHandles_capacity * 2 : 16;
+        NewFileHandleEntry_t *newEntries = realloc(NewFileHandles_entries, newCapacity * sizeof(NewFileHandleEntry_t));
+        if(!newEntries)
+            return NULL;
+        NewFileHandles_entries = newEntries;
+        NewFileHandles_capacity = newCapacity;
+    }
+
+    uintptr_t token = ++NewFileHandles_lastToken;
+    NewFileHandleEntry_t *entry = NewFileHandles_entries + NewFileHandles_count++;
+    entry->token = token;
+    entry->kind = kind;
+    entry->object = object;
+    return (void*)token;
+}
+
+/* Answer the object of the token if the token is live and of the kind, else NULL. */
+static void *
+NewFileHandles_lookup(int kind, void *token)
+{
+    ptrdiff_t index = NewFileHandles_find((uintptr_t)token);
+    if(index < 0 || NewFileHandles_entries[index].kind != kind)
+        return NULL;
+    return NewFileHandles_entries[index].object;
+}
+
+/* Like lookup, and take the entry out of the table.  The caller frees the object. */
+static void *
+NewFileHandles_release(int kind, void *token)
+{
+    ptrdiff_t index = NewFileHandles_find((uintptr_t)token);
+    if(index < 0 || NewFileHandles_entries[index].kind != kind)
+        return NULL;
+
+    void *object = NewFileHandles_entries[index].object;
+    memmove(NewFileHandles_entries + index, NewFileHandles_entries + index + 1,
+        (NewFileHandles_count - (size_t)index - 1) * sizeof(NewFileHandleEntry_t));
+    --NewFileHandles_count;
+    return object;
+}
+
+#endif // PHARO_NEWFILE_HANDLES_H
